# Camera reliability and network boundary

Tested 2026-09-12 on the locally built studio at `http://127.0.0.1:4173/`.

The [70-second browser test](tracking-recovery-smoke.json) initializes the actual face, pose and hand tasks using Chromium's synthetic camera. Tracking remains active beyond one minute, stops with every acquired track in the `ended` state, restarts, and releases tracks again. No camera is acquired automatically; both requests explicitly specify `audio: false`. This is infrastructure evidence, not real-face tracking, physical device recovery or sustained production acceptance.

Eight camera lifecycle tests in `tests/camera.test.ts` cover late permission results, Stop during video playback initialization, an old playback rejection after restart, retired disconnect/error callbacks, stale/duplicate inference results, one pending frame, bitmap disposal, denied permission recovery and exact timeout behavior. Six worker tests additionally check delegate initialization/cleanup, explicit CPU execution, epoch timestamp rebasing, sampling cadence and frame disposal. Two server-watch tests cover health-probe recovery, idle behavior and watcher disposal. The focused camera/worker/server-watch run passes 16 tests, and the production TypeScript/Vite build passes.

The camera class checks session identity after each asynchronous startup boundary. Retired callbacks cannot stop a replacement camera. Replies must match the pending frame timestamp, and a worker timeout releases the stream. Model initialization and the first inference each retain a **60-second** deadline. Every subsequent inference has a **30-second** deadline: the [positive-photo diagnostic](tracking-positive-fixture.md) measured 18.79 seconds of cold positive inference, which could occur after startup had already returned empty detections. The previous 15-second deadline could terminate that work prematurely. The timeout regression accepts a slow positive reply after an empty one, verifies that a later unanswered frame remains active at 29,999 ms, and releases its stream/worker at 30,000 ms. This allows cold work to finish; it does not claim that such latency is acceptable for normal live tracking.

The outgoing frame clock is `performance.timeOrigin + performance.now()`. Before accepting another frame, the camera requires at least 50 ms (balanced) or 100 ms (low power) beyond the previous accepted timestamp. The one-pending-frame guard is set before asynchronous bitmap creation; generation checks discard a bitmap belonging to a stopped session. Consequently, equal or earlier timestamps cannot be sent by this camera path: they fail the existing interval check. Pose/hand calls use a subsequence of those timestamps, and camera restart creates a new worker. SDK calls now receive a session-relative clock while frame/sample freshness keeps the original epoch. No additional timestamp counter or speculative ordering machinery was needed.

## Local-only enforcement

All tracking models and WASM load from the local server. The shared policy in `config/http-policy.json` applies to both the document and worker scripts. It allows same-origin requests and in-memory `blob:`/`data:` assets, including embedded VRM textures. External connection attempts are denied by Content Security Policy. Development additionally permits its local Vite WebSocket; production has no external destination exception.

MediaPipe's current [privacy notice](https://github.com/google-ai-edge/mediapipe#privacy-notice) describes utilization/performance metrics, while keeping input processing on device. The installed 1.0.1 bundle contains a logger targeting `odml.pa.googleapis.com` with a 60-second flush timer. An upstream maintainer explicitly [permits blocking outgoing telemetry requests while continuing to use the SDK](https://github.com/google-ai-edge/mediapipe/issues/6306#issuecomment-4673728357). We enforce the boundary rather than assuming a library has no telemetry code.

The browser test runs beyond that timer, monitors context requests/responses, and aborts any external request as a second test-only guard. It observes zero external requests or responses during this run. Deliberate probes to a reserved external domain are rejected in both the document and tracking worker before reaching the test guard. The guard itself intercepts zero requests, demonstrating that the served policy provides the tested boundary. The test does not certify unrelated browser extensions, other programs or future remote voice features.

## Remaining acceptance

Camera resolution is selectable between 640×480 and 1280×720. TrackingFrame v1 includes sequence numbers and separate face/pose/hand sampling timestamps, durations and presence; pose visibility and hand scores remain attached to observations. The later 70-second test includes this contract. [Installed CPU execution](tracking-cpu.md), [positive GPU/CPU photo results](tracking-positive-fixture.md), and [production server-loss release](server-stop.md) now provide additional component evidence. Physical permission/device/busy-camera checks, real gestures, actual GPU-unavailable fallback behavior and the complete integrated soak remain open in TASK-003/009/020. TASK-009 stays active; these component checks do not close the remaining acceptance.
